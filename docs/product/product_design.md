# MAI 产品设计文档

> 当前状态：稳定实现版。配套技术文档见 [`../architecture/technical_design.md`](../architecture/technical_design.md)；Story World 子产品见 [`story_world.md`](story_world.md)；内置人设清单见 [`personas.md`](personas.md)。

## 1. 产品定位

MAI 是一个本地优先的多模型协作讨论平台。用户把多个 AI 人设拉进同一个讨论室，让它们按阶段和赛制互相回应、质询、总结，并把过程沉淀为可追溯的消息、裁决、书记官状态和子讨论结论。

它不是简单的模型并排对比工具。核心差异在于：

- 模型之间共享上下文并真正互相对话。
- 发言由阶段规则调度，而不是自由乱跑。
- 用户始终拥有裁决、冻结、阶段推进和模型配置的最终控制权。
- 讨论结果以 append-only 的方式保留，便于复盘。

## 2. 产品原则

1. **用户掌控感优先。** AI 可以自动推进，但每个自动行为都要能被用户打断、冻结、继续或覆盖。
2. **模板沉淀价值。** 人设、阶段、赛制、配方、API 模型配置都是可复用资产。
3. **内置只读，实例可改。** 内置模板是产品提供的起点；用户从内置库复制后得到自己的可编辑实例。
4. **append-only。** 消息、裁决、撤销、死路标记和主持信号都以新记录追加，不做历史编辑。
5. **界面语言要面向用户。** 内部枚举如 `round_robin`、`facilitator_suggests`、`user_manual` 只出现在数据层；界面显示友好的中英文文案。

## 3. 核心对象

| 概念 | 说明 | 生命周期 |
|---|---|---|
| Persona Template 人设模板 | AI 角色定义：角色类型、系统提示词、温度、健谈度、模型选择、主题色、图标、标签 | 全局复用 |
| Persona Instance 人设实例 | 加入房间时从模板复制出的快照（含主题色与图标）；房间内修改不污染模板 | 房间内 |
| Phase Template 阶段模板 | 单个阶段的发言范围、排序规则、退出条件和行为提示 | 全局复用 |
| Debate Format 赛制 | 一组阶段模板的有序组合 | 全局复用 |
| Recipe 配方 | 人设集合、赛制和初始设置的打包 | 一键开房 |
| Room 讨论室 | 一次具体讨论，包含消息、阶段计划、成员和运行时状态 | 讨论实例 |
| Scribe State 书记官状态 | 共识、分歧、问题、决议镜像、产物、死路 | 房间内 |
| Facilitator Signal 主持信号 | 面向用户的讨论健康度和节奏建议 | 房间内 |
| ApiProvider / ApiModel | API 凭据与模型清单 | 全局设置 |
| Tool Server / Tool Invocation | MCP server 注册、工具清单和每次工具调用审计 | 全局 / 房间内 |
| Scenario 场景 | 预置标题、初始问题、赛制或配方的一键开房入口 | 全局内置 |
| World 世界 | 跨房间的世界观容器（synopsis、setting、calendar_hint），承载若干角色与场景 | 全局，跨房间 |
| World Bible 世界设定集 | World 的结构化状态：世界概述、背景、当前时间、当前地点、主线 Arc、地点、阵营、规则、伏笔 | World 内 |
| Timeline Event 时间轴事件 | World 级事件：历史背景、记忆/关系/伏笔/主线/地点/阵营变化；Scene 节点仍以 Room 为源 | World 内 |
| Seal Draft 封幕草稿 | Scene 结束时由 LLM 生成的可编辑状态变更草稿，用户确认前不写入长期世界状态 | Scene 内 |
| World Character 世界角色 | World 自带的角色档案：core_identity、skills、goals、外观；`kind=ai` 绑定 PersonaTemplate，`kind=user` 由用户驱动 | World 内 |
| Scene 场景 | 一幕戏 = 一个带 `world_id` + `scene_index` 的 Room；通过 `WorldSceneMember` 名册控制在场角色 | World 内 |
| Character Memory 角色记忆 | 跨场景的三层记忆：core_identity（手写）/ relationships（关系卡片）/ episodic（封幕 scribe 写入） | World 内 |

## 4. API 与模型配置

模型配置分两层：

| 层级 | 作用 | 示例 |
|---|---|---|
| `provider` | 凭据 + LiteLLM 路由类型，由用户起一个可读名称 | "我的 OpenAI"，类型 `openai` / `anthropic` / `openrouter` / `custom` |
| `model` | 具体模型条目 | `openai/gpt-4o-mini` |

用户在 API 配置页维护 provider 和模型列表，再在人设页或房间成员编辑器里选择模型。设置页只负责选择全局默认模型。一个 provider 下可以挂多个模型，多个 provider 也可以共存。

调用模型时的产品语义：

1. 房间内 `PersonaInstance.api_model_id` 绑定的模型优先。
2. 未绑定时使用设置页 `AppSettings.default_api_model_id`。
3. 旧数据的 `backing_model + api_provider_id` 仅作为兼容回退。

人设模板上的模型选择会在创建房间或 Scene 时复制到房间内人设实例；之后修改模板只影响未来新建实例，不会回溯改写既有房间的模型路由。

## 5. 模板体验

模板页包含五个页签：

- 人设
- 阶段
- 赛制
- 配方
- API 配置

前四个模板页采用同一规则：

- 默认显示用户可编辑实例。
- 卡片可点击进入右侧编辑器。
- 可编辑实例可以修改或删除。
- “添加”打开内置库，选择后复制一份。
- 内置模板不可直接修改；后端也以 403 保护。

阶段模板的关键配置：

- `allowed_speakers`：所有角色、变量绑定、指定人设。
- `ordering_rule`：轮流、交替、提及驱动、用户指定、问答配对、并行。
- `exit_conditions`：轮次、全部发言、全部投票、token 预算、主持建议、手动推进。
- `auto_discuss`：允许 AI 在该阶段连续接力，直到退出条件或运行时上限触发。
- `auto_discuss_mode`：`decay` 表示 casual 自动讨论会逐步衰减，`continuous` 表示持续接力直到退出条件或上限。

赛制是阶段的顺序组合，配方是“人设 + 赛制 + 初始设置”的组合。

## 6. 讨论室体验

房间主界面采用三栏：

- 左侧：房间列表。
- 中间：消息流和输入框。
- 右侧：成员和状态。

房间设置抽屉包含：

- 阶段计划
- 书记官状态
- 主持信号
- 裁决
- 工具与 MCP
- 限额
- 文档上传
- 子讨论

讨论推进规则：

- 用户消息、文档消息、群友发言等会触发 autodrive。
- AI 消息不会递归触发下一轮，避免队列失控。
- `auto_discuss=True` 的阶段可让 AI 连续接力，但受 `max_consecutive_ai_turns` 和退出条件限制。
- casual ordering 默认使用 `auto_discuss_mode=decay`，适合闲聊；故事/演出型阶段使用 `continuous`，避免依赖 `tags` 改变调度语义。
- `parallel` 阶段允许多个 AI 同时发言，每条消息独立流式渲染。
- Freeze 会取消当前 in-flight 调用并冻结房间。

消息列表上方有一条**发言状态条**，提供运行时状态机的可视化：

- `frozen`：房间冻结，提示"解冻才能继续"。
- `speaking`：当前发言人头像 + 「『某某』正在思考…」，整条用该角色主题色染。
- `scheduling`：autodrive 已经持锁但还没产生第一个 chunk —— "正在挑选下一位发言者…"。
- `idle`：autodrive 没在跑，提供 「让 AI 继续」 按钮，让用户不发消息也能让 AI 接力（背后调 `POST /rooms/{id}/autodrive/resume`）。

旁边显示连续接力计数 `已连续 X / N 轮`。状态条里的**暂停**是 graceful pause：先阻止 autodrive 排下一位，等待当前角色说完，再把房间置为冻结；顶部**冻结**仍是强制控制，会立即取消当前 in-flight 调用。

### 6.1 故事模式

故事模式是一个特殊的 phase + format（`story_mode` / `story_format`）：

- 单 phase 永不自动退出，由用户喊停。
- casual ordering 但跳过几何衰减——AI 会持续接力，直到达到连续上限、token 预算上限或用户冻结。
- 系统提示明确要求保持角色一致：每次只演自己的台词和动作，不替别人发言；可以用 `*...*` 描写动作，确实没词时输出 `<silent/>` 让别人接，但默认应该用一句话或一个动作维持存在感。
- 多 AI 房间下，每个 AI 看到的历史对白会重写：自己的过去发言保留为 `assistant`，其他人的发言改成 `user` 并加 `「名字」: ` 前缀，从根上避免出现"全知叙述者"现象（一个 AI 把所有人的对白都写出来）。

适合：剧本演练、虚构对话、群聊推演、人物原型互动。

### 6.2 Story World

Story World 在 Room + Persona 之上加一层 **World** 容器，把单次房间重新定义为该世界中的一幕 **Scene**，并给世界中的角色一条跨场景的记忆线。完整设计见 [`story_world.md`](story_world.md)。要点：

- 普通讨论房 (`world_id IS NULL`) 行为完全不变，Story World 是纯增量层。
- 同一 World 内 Scene 严格线性 (`scene_index` 单调递增，无分支)。
- 角色档案分两种 kind：`ai`（绑定 PersonaTemplate，跑记忆管线）、`user`（用户驱动的轻档案，无 episodic）。
- Composer 增加两种模式：**旁白**（用户作为导演描写场景 / 动作，落库为 system 消息）和**扮演**（用户挑选 `kind=user` 角色以其身份发言）。
- 每幕显式封幕（`POST /rooms/{rid}/seal`）先生成 Seal Draft，不直接写入长期状态。
- **Scene-end Inspector** 中用户检查 / 编辑摘要、时间轴事件、角色记忆和关系变化；确认 commit 后才写回 Timeline、Memory、Relationship 并锁定 Scene。
- World Detail 是世界主控台：展示当前时间点、主线 Arc、最近 Scene、活跃角色、Timeline、World Bible、角色记忆和关系网列表，并提供继续当前 Scene / 开启下一幕入口。

## 7. 工具、MCP 与能力权限

MAI 引入一个轻量工具层，用来把外部能力接入房间讨论，并把权限控制落到具体房间成员。

工具来源分两类：

- MAI 内置工具：读取房间消息、读取成员列表，以及在显式授权时创建模板。
- MCP server：用户在房间工具面板中添加 URL，选择 `streamable_http` 或 `sse`，同步后进入工具清单。

权限不放在全局开关里，而是落到房间成员实例：

- `允许自动回复`：关闭后自动调度跳过该成员，适合只想手动点名的专家。
- `允许工具`：开启后，该成员的 LLM 调用会收到工具定义。
- `允许写入工具`：开启后才能调用会修改 MAI 数据或外部系统的工具。

工具调用本身是房间消息流的一部分。每次调用都会追加 `tool_invocation` 记录，显示工具名、参数、状态、结果或错误。这样能力扩展不会变成黑箱，用户可以复盘某个 AI 为什么得出结论。

## 8. 场景与模板起草

首页新建房间提供场景入口。场景不是新对象实例，而是产品内置的启动预设：

- 技术方案评审
- 产品决策圆桌
- 发散头脑风暴
- 假设压力测试

场景会预填房间标题、初始问题、赛制或配方。用户仍可在创建前修改成员和模板选择。

模板页提供自然语言起草入口。当前已接入人设草稿：用户描述想要的角色，系统生成名称、描述、系统提示词、温度、标签和配置 JSON，用户确认后再保存。后端接口保留 phase / recipe 草稿类型，后续可以扩展到完整模板创建向导。

## 9. 用户权力

### 裁决者

Judge 模式允许用户写入裁决。裁决会同步进入 `decisions` 表。撤销裁决不会修改原消息，而是追加 `verdict_revoke` 消息，并把 `Decision.revoked_by_message_id` 指向撤销消息。

### 死路标记

用户可以把某个方向标记为 dead end。它以消息形式追加，书记官后续会折叠进 `ScribeState.dead_ends`。

### 群友发言

用户可以用临时昵称投放观点。AI 视图里它就是普通讨论消息；只有用户复盘界面可揭示身份。

### 冻结

冻结是最高优先级控制：

- 取消当前 in-flight 调用。
- 保存已生成 partial 为 truncated message。
- 房间进入只读冻结态。
- 用户可稍后解冻继续。

暂停是冻结的温和入口：它不取消当前 in-flight 调用，而是等当前角色自然完成后进入冻结态，避免故事模式里一句台词被截断。

## 10. 系统角色

### 书记官 Scribe

书记官每 5 条可见消息和阶段边界运行一次，使用结构化 tool call 把新消息折叠进：

- 共识
- 分歧
- 开放问题
- 决议镜像
- 产物
- 死路

书记官只记录已经发生的内容，不提供建议。

### 主持 Facilitator

主持同样按节奏运行，也可由用户主动询问。它输出面向用户的信号，例如：

- 当前阶段是否空转
- 是否出现新共识
- 是否偏题
- 是否适合开子讨论
- 是否需要 red team
- token 或节奏是否接近风险

主持信号对讨论 AI 隐藏，避免污染论证。

## 11. 子讨论

子讨论用于隔离独立争议点。子房间拥有独立消息、阶段和书记官状态。合并回父房间时，用户填写或确认：

- 结论
- 关键推理
- 未解决问题

父讨论看到的是结构化合并包，而不是整段子讨论上下文。

## 12. 文档上传

v1 支持：

- Markdown
- TXT
- PDF

上传后端会提取纯文本，并以 `user_doc` 消息加入房间。AI 看到的是提取文本，不直接读取原文件。

当前不做：

- 图片上传
- OCR
- 多模态消息

## 13. 国际化

界面支持中文和英文：

- 语言状态保存在浏览器 `localStorage`。
- 全局导航和房间头部都提供切换入口。
- 页面文案、按钮、状态、内部枚举显示都走 i18n。
- 用户内容、模板名称、房间名称不自动翻译。

## 14. 当前边界

这些功能当前不做，除非产品方向重新确认：

- 消息编辑 / 删除。
- 倒带与任意分支。
- 多用户协作。
- 节点连线式赛制编辑器。
- 模板导入 UI。
- Trace 查询与重放 UI。
- 图片 / 多模态上传。
- 移动端专项适配。
- Streaming 续写。
- 超时自动重试。

这些边界不是技术不能做，而是为了保持单进程、本地优先和可控体验。
